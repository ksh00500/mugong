# 첫 브라우저 플레이 버전 검증

후속 변경과 최신 검증은 [전투 연출·UI 개선](ui-combat-polish-v1.md)을 참조한다. 아래는 첫 플레이 버전 시점의 기록을 유지한다.

2026-09-28. Node.js 22.16, Windows, Chromium 153. 실제 설치 버전은 package-lock.json에 고정한다.

## 최종 결과

| 검증 | 결과 |
|---|---|
| `npm test` | 3개 파일, 25개 테스트 통과 |
| `npm run test:e2e` | 9개 실제 브라우저 시나리오 통과, 45.5초 |
| `npm run build` | TypeScript 검사 및 Vite 빌드 성공 |
| `npm ls --depth=0` | 의존성 오류 없음 |
| 설치 시 npm audit | 알려진 취약점 0건 |

규칙 테스트는 Lv.0 시작, 동일 카드 복원, 무공 개수·레벨 상한, 300개 난수 시드의 경험치 예산, 지연 공격·중복 타격·궁극기 조건, 무공 전환 상태, 수납 회전·충돌·중첩·연결 해제, 전투 중 사용 금지, 귀환 HP·수명과 만료 회수, 저장 실패 재시도를 검증한다. 별도 전투 시뮬레이션은 적 HP·플레이어 HP·전투 결과를 강제로 바꾸지 않고 합법적인 입력과 회복·성장 선택으로 20웨이브를 완주한다. 이것이 모든 빌드와 난수 시드의 난이도를 보장하지는 않는다.

브라우저 테스트는 생성·이동·전투 가방·새로고침, 실제 공격으로 첫 성장·카드 선택·전리품 수납·다음 웨이브, 정리판 폐기 취소·회전, 적 몸통을 클릭한 좁은 찌르기, 최종 보스 처치·명부·창고 이동, 사망 결과 복원, 두 탭의 쓰기 충돌, 화면 크기별 가로 넘침, 캡처·프레임 시간을 확인한다. 시나리오 준비에는 격리된 테스트 브라우저의 IndexedDB에 유효한 상태를 넣으며 게임에 디버그 치트 API를 노출하지 않는다. 전체 캠페인의 규칙 검증과 개별 화면 흐름의 브라우저 검증을 구분한다.

## 성능

1440×900, 헤드리스 Chromium, SwiftShader 소프트웨어 그래픽에서 18웨이브 적 9명을 표시하고 requestAnimationFrame 120회 시간을 기록했다. 빈 페이지 기준 약 60.0FPS, 전투 화면 평균 41.8FPS(23.95ms), 95백분위 33.4ms였다. 측정 기록은 [frame-timing.json](verification/frame-timing.json)에 보관했다.

처음에는 소프트웨어 WebGL에서 약 9FPS로 나타났다. 소프트웨어 감지·960×540 Canvas 전환·불투명 배경 합성으로 개선했다. 자동 검증의 현재 성능 하한은 평균 30FPS이며 60FPS 목표 달성을 의미하지 않는다. 그래픽 가속 기기에서의 지속적인 60FPS, 다수의 공격 효과·이기어검이 동시에 나오는 상황, 모바일 기기의 성능은 추가 확인 대상이다. CSS 배경의 지역 색 변화와 Canvas 배경의 색감에는 작은 차이가 있다.

## 화면 검토

1440×900 로비·전투·무공 카드·가방을 캡처해 확인했다. 1024×768 및 390×844에서 페이지 가로 넘침을 검사했다. 작은 화면에서 읽고 표시할 수 있지만 터치 플레이 지원을 뜻하지 않는다. 캐릭터는 작은 크기로 표시하며 맵 전체가 고정 화면에 들어온다.

이미지는 현재 첫 플레이용이다. 걷기·베기의 소수 키프레임, 색 변화 피격, 회전 사망 자세, 기존 적 시트를 활용한 보스 표시를 사용한다. 무공별 고유 애니메이션과 전용 보스 원화, 실제 사람의 플레이를 통한 공격 리듬·회복량·난이도 조정은 이어서 진행한다.

계정·온라인 레이드·PVP·시장·모바일 앱은 이 버전의 구현 범위에 포함되지 않는다. 저장은 브라우저와 사이트 주소별로 분리되며, 강제 종료 직전 약 1초의 진행은 복구되지 않을 수 있다. Web Locks를 지원하지 않는 환경은 탭 간 쓰기 잠금을 보장하지 않는다.
