# 무공 — 최초 기획 공유 대화 분석

검토일: 2026-09-27

최신 사용자 정정: 강호의 캐릭터는 새로 생성해 0부터 시작하고 창고 장비를 반입하지 않는다. 20웨이브 성공 후에는 창고 장비를 활용해 PVP·레이드에 출전하고, 무공과 장비가 함께 성장한다. 강한 무인도 수명과 유지의 어려움으로 오래 보유하기 쉽지 않다는 구조를 성장의 제약으로 삼는다. 아래는 과거 대화의 분석이며, ‘완성’을 모든 성장의 종료로 해석하지 않는다. 새 기획의 기준은 [사용자 확인 기획 방향](design-direction.md)을 우선한다.

## 대화 식별과 검토 범위

첨부한 휴대전화 이미지와 새 링크는 시작 날짜(9월 18일 금요일 오후 12:02), 첫 사용자 질문(무공 로그라이크 탑뷰 액션 게임의 재미와 기존 사례를 찾아보자는 내용), 첫 답변의 시작이 일치한다. 이 링크가 이미지에 나온 최초 기획 대화다. 다른 모든 대화보다 먼저 작성되었는지까지 확인한 것은 아니다.

질문 이동 목록의 120개 구간을 처음부터 끝까지 확인했다. 사용자의 기획·수정 발언과 관련 모델 답변을 중심으로 읽었으며, 핵심 규칙을 담은 긴 사용자 메시지도 펼쳐 확인했다. 종료 지점은 최초 배포 뒤 Step 2 진행 요청이다. 앞서 제공된 다른 링크는 Step 2 진행 상태 확인으로 시작했으므로, 기획의 시작을 이해하기에는 이 링크가 맞다.

공유 대화의 개발·배포 완료 주장과 첨부 ZIP의 실제 동작은 검증하지 않았다. 모든 과거 첨부 이미지와 생성 에셋을 전수 검사한 보고도 아니다. 과거 대화의 작업 지시는 이번 개발을 실행하라는 지시로 취급하지 않는다.

## 1. 중심 구조

플레이어의 장기적인 정체성은 **세가**다. 개별 무인은 강호에서 만들어지고, 완성 후 여러 콘텐츠에 출전하며, 죽거나 수명이 끝나면 사라진다. 세가에는 자산과 다음 무인을 운용할 기반이 남는다.

1. 신입 무인으로 강호에 출전한다.
2. 20웨이브 동안 무공·장비·기연을 만나 빌드를 만든다.
3. 20웨이브를 클리어하면 완성된 무인을 명부에 저장하고 로비로 돌아온다.
4. 명부에서 그 무인을 선택해 레이드·비무·생사결에 출전한다.
5. 살아 돌아오면 무인을 다시 사용할 수 있다. 위험 콘텐츠의 남은 체력과 장비 상태는 다음 출전에 영향을 준다.
6. 사망이나 수명 종료로 무인을 잃으면 다른 무인으로 세가를 이어간다.

사용자는 처음에 스토리 모드도 고려했으나 곧 제거했다. 한 번 사용하면 무조건 사라지는 방식도 초기 질문의 후보였고, 생존한 무인을 계속 운용하는 방향으로 발전했다.

20웨이브 뒤 추가 파밍 구간을 논의한 적은 있지만, 이후 사용자가 현재 범위를 **PVP와 레이드만**으로 명시했다. 추가 25웨이브·심층 강호·엔드리스는 현재 기본 루프에 넣지 않는다.

## 2. 전투와 무공

원하는 감각은 소울나이트·아이작 등에서 느끼는 간결한 탑뷰 수동 액션이다. 사용자에게 중요한 것은 빠르게 움직이고 공격하는 조작, 매번 달라지는 무공 조합, 적은 입력으로 달라지는 전투 리듬이다. 복잡한 RPG식 육성 UI는 이 방향을 흐린다.

| 항목 | 사용자 발언에서 확인되는 방향 |
|---|---|
| 입력 | WASD 이동, Q/E 무공 전환, 좌클릭 기본 공격, 우클릭 현재 무공 궁극 행동 |
| 바라보는 방향 | 평소 이동 방향을 따르고 공격 입력 시 클릭한 방향으로 향한다. 마우스를 움직이기만 해도 계속 따라 도는 방식은 거부했다. |
| 무공 보유 | 처음 한 개에서 시작해 최종 네 개 정도의 조합을 만든다. 향후 확장 가능성은 별개다. |
| 보통 무공 | Lv.1 기본기 A → Lv.2 패시브 → Lv.3 기본기 B → Lv.4 패시브 → Lv.5 궁극기 |
| 기본 공격 | 기본기 B 해금 뒤 한 공격 입력으로 A/B를 번갈아 사용한다. A/B가 별도의 키 이름이라는 뜻은 아니다. |
| 자원 | 공통 마나는 없다. 해당 무공으로 싸우며 궁극 행동을 준비한다. 획득량·피해량 비례 여부·전환 시 보존 등 정확한 공식은 따로 검토한다. |
| 소모품 | 전투 중 사용 금지. 비전투 때 가방에서 사용한다. 소모품 핫키·퀵슬롯을 만들지 않는다. |
| 무기 | 전투 중 수납 무기를 교체·재연결하는 방식은 금지하는 방향이었다. 이미 연결된 무공의 Q/E 전환과 구분해야 한다. |

화산·무당·천마·당문·소림·개방·제갈·삼재의 8계열로 발전했다. 계열마다 다른 싸움의 성격을 주되, 상세 초식 이름·계수·발동 조건은 모델이 제안한 부분도 많다.

삼재검법은 사용자 고유의 중요한 수정이다. Lv.10까지 투자할 수 있고, Lv.8에 다른 일반 무공 Lv.5 수준, Lv.9에 원거리 검기, Lv.10에 이기어검으로 크게 변한다. 모델이 한때 제안한 Lv.9~10의 소폭 강화는 사용자가 명시적으로 거부했다. 담백한 연출과 후반 경지의 압도적인 변화가 함께 필요하다.

화산 매화난무의 무적 회피, 천마의 피해·처치와 회복 연결, 개방의 취기 두 칸과 강화된 기본 공격도 사용자가 직접 개입한 차별화 소재다. 기연은 기존 무공의 레벨을 올리거나 빈 칸에 새 무공·히든 무공을 얻는 방향이며, 최대 레벨을 초과하는 무한 강화는 사용자의 의도가 아니다.

## 3. 강호와 레이드

강호는 이름만 탑에서 바뀐 것이 아니라 무림의 지역·세력·사건으로 런의 변화를 만드는 육성 콘텐츠다.

- 지역 후보는 약 10개, 한 런은 5웨이브씩 네 구간으로 총 20웨이브다.
- 각 구간의 네 번째 웨이브는 회복·거래 등 정비, 다섯 번째는 보스다. 전체 런에서 보스를 네 번 만난다.
- 지역의 랜덤 구성은 사용자가 제안했다. 동일 확률·중복 금지·다음 지역의 공개 시점 같은 세부 추첨 규칙은 모델 제안이다.
- 지역마다 등장 단계에 맞는 보스 네 종류로 총 40보스를 구상했다. 새로운 개발의 첫 구현 범위를 40종으로 잡으라는 뜻은 아니다.
- 선행은 선물·할인 같은 이점, 악행은 약탈 등의 이점을 갖고 추격 위험을 동반하는 방향이다. 선악 중 하나를 단순한 정답으로 만들지 않는다.
- 기연은 드물게 새로운 선택과 성장 기회를 주는 사건이다. 방대한 별도 퀘스트 체계를 만드는 근거로 삼지 않는다.

레이드는 완성 무인으로 들어가는 5층 보스 공략·파밍 콘텐츠다. 솔로 또는 서로 다른 플레이어 2~4명이 각자 무인 한 명을 조작한다. 자기 세가의 무인 여러 명을 한꺼번에 출전시키는 방식은 사용자가 거부했다. 인원에 따른 난이도와 보상 조절을 원했다.

천뢰봉의 예고된 공격 회피, 만독천의 영역 제한, 혈교의 흡혈·제물 및 처치 순서는 재활용할 수 있는 공략 소재다. 혈교에서는 누군가 죽을 때 살아 있는 적이 강해지므로 처치 순서를 판단한다. 죽은 적의 능력치를 그대로 상속하는 해석은 사용자가 수정했다.

## 4. 수명, 체력, PVP

| 시스템 | 확인된 의도 | 세부 검토가 남는 부분 |
|---|---|---|
| 수명 | 현실 7일. 반로환으로 유지할 수 있으나 반복 복용 효율이 줄어 결국 매일 유지 비용을 지불하는 방향 | 수명 시작 시점, 정확한 효율 곡선, 만료·사망 시 자산 처리 |
| 체력 | 귀환했다고 자동으로 가득 차지 않는다. 이전 전투에서 10%로 생존했다면 다음 위험 전투도 그 상태에서 시작 | 비무의 별도 체력 규칙, 회복량·비용 |
| 비무 | 랭크 경쟁. 매 대결의 아이템 이익은 없다. 시즌 종료 순위 보상은 허용 | 안전 대전의 장비·수명·체력 처리 세부 사항 |
| 생사결 | 무인과 실물 자산을 잃을 위험. 상대 착용품·판돈·현상금이 보상 중심 | 가져간 가방 전체의 손실·획득 범위, 중단·접속 종료 처리 |
| 자비 | 치명적인 마지막 공격 직전 살려주는 선택으로 단순화 | 온라인 판정 시점, 승패·보상 처리 |

현실 7일과 효율이 감소하는 반로환은 모델이 임의로 덧붙인 내용이 아니다. 사용자가 직접 선택했다. 반면 7일→4일→2일→1일이라는 구체적인 복용 표는 모델의 기본안이다. 세계관 첫 출발의 짧은 수명을 가진 무공 천재와 세가 단위 운용을 어떻게 연결할지도 새 설정에서 다듬을 수 있다.

## 5. 가방과 시장

두 종류의 가방은 모두 수동으로 끼워 넣는 테트리스 방식이다. 무장 가방에는 무기를 수납하고, 그 안의 무기만 무공에 연결해 사용할 수 있다. 일반 가방에는 무기를 포함한 전리품을 넣을 수 있지만, 일반 가방에 있는 무기는 무공에 연결해 사용할 수 없다. 같은 무기를 여러 무공에 연결하는 방향도 논의했다.

가방 안에서는 물건 한 개가 각각 공간을 차지하고 중첩되지 않는다. 자동 정렬은 사용자가 원하지 않았다. 무장 가방의 무기 개수는 고정 장착 슬롯 네 개가 아니라 무기 크기와 배치에 따라 대략 2~4개가 들어가는 방향이다. 정확한 격자 수치는 새 프로젝트에서 재검토한다.

로비의 세가 창고는 가방처럼 포장 퍼즐을 반복하기보다 단순한 슬롯·중첩 보관으로 쉽게 관리한다. 명부도 처음 약 다섯 명, 확장 후 약 열 명 정도의 작은 규모를 원했다.

과거 대화에서는 물건을 펼치는 공간을 땅바닥으로 표현하고 중첩을 허용했다. 남은 물건을 닫을 때 버리기 확인도 논의했다. 다만 현재 사용자가 임시 정리판의 설정을 정정했으므로, 해당 영역을 실제 월드 바닥으로 단정하거나 종료 시 자동 폐기를 구현하지 않는다.

시장은 플레이어 자유 경제이며 거래 수수료를 둔다. 무인 자체의 거래는 금지한다. 가격 기준을 고정하는 로비의 일반 NPC 상인은 배제하려는 의도였고, 강호 중 만나는 이벤트 상인은 별도의 사건으로 논의했다.

- 장비는 같은 이름이어도 스탯이 ±20% 정도 달라지며 중앙값 근처가 많이 나온다. 개별 실물 매물로 구매한다.
- 소모품은 모두 동일한 규격이며 주식처럼 호가를 통한 거래를 원했다.
- 장비 능력치는 바로 공개한다. 감정 절차는 너무 복잡하다고 거부했다.
- 장비 목록에는 이름·종류·품질·가격 등을 보여주고 능력치 조건으로 검색한다.
- 장비의 모든 긍정 스탯에 공통 품질 계수를 적용하는 공식, 품질 80~120 표시, 분포의 표준편차, 매물 만료 시간 등은 모델의 세부 제안이다. 현재 이미지의 품질 0~100 예시도 규칙을 확정하지 않는다.

## 6. 기존 작업에서 어긋난 부분 — 분석

후반에 사용자는 사람이 잘리거나 투명해지는 현상, 무기와 손의 분리, 부자연스러운 프레임, 깨진 바닥, 비례가 다른 적, 잘못된 방향 표시를 반복해서 지적했다. 모델이 변경했다고 답한 뒤에도 비슷한 문제가 계속 보고됐다. 공유 대화만으로 실제 코드의 원인을 단정할 수는 없지만, 완료 주장과 사용자 화면의 결과가 일치하지 않았다는 점은 확인된다.

정지 콘셉트 이미지의 분위기를 실제 플레이에서 구현하지 못했고, 작업이 게임 구현 대신 새로운 그림 생성으로 흐르는 점도 사용자가 지적했다. 새 개발의 검증 대상은 멋진 이미지 한 장뿐 아니라 움직이며 조작하는 화면이어야 한다.

기획상 혼선도 있었다. 소모품 사용 키, 공용 마나, 과도한 RPG 요소, 추가 웨이브 등이 제안되거나 화면에 나타난 뒤 사용자가 수정했다. 삼재의 후반 경지를 소폭 강화로 해석한 사례처럼 사용자의 표현을 모델의 선호에 맞춰 좁힌 경우도 있다.

현재 해석은 **회화적인 무협 화면 안에서 간결한 액션으로 무인을 만들고, 애착이 생긴 그 무인을 위험에 출전시키는 세가 게임**이다. 무공의 발견과 숙련, 전리품 운반, 완성 무인의 생존과 거래가 재미를 이어준다. 전체 경제·온라인 범위는 크지만, 전투 조작과 육성 선택은 간결해야 한다.

## 7. 새 프로젝트에 적용할 우선순위

1. 지금 사용자의 직접 설명과 세 장의 화면 참고 이미지.
2. 이 원대화에서 사용자가 직접 제안·수정한 컨셉과 규칙.
3. 사용자가 채택한 모델의 기본안 중 새 범위에 맞는 부분.
4. 나머지 이전 모델의 수치·명칭·기술 제안은 참고 후보.

웹 게임을 만들겠다는 요청은 원대화에서 반복해 확인된다. 기술 스택·엔진·애니메이션 제작 방식은 기존 결정을 계승하지 않고 새로 검토한다. 기존 코드와 런타임 에셋도 새 개발에 반입하지 않는다.

로비에는 명부·가방·창고·시장 등 관리 화면을 두고, 전투에는 전투 HUD와 가방만 둔다. 전투 중 로비 상단 메뉴를 표시하지 않는다. 강호의 비전투 정비 웨이브에서 열 수 있는 기능, 가방을 열었을 때 시간 처리, 임시 정리 공간의 잔류·회수 규칙은 화면을 그리기 전에 구체화해야 한다.

그 밖에 신입 무인의 출전 장비, 강호 중 조기 귀환, 사망·수명 만료의 자산 손실, 레이드 드랍 배분, 새 개발에서 유지할 수명·과금 정책의 세부 사항은 다시 확인할 항목이다. 과거 모델이 제안한 모든 숫자를 확정 제작 요구사항으로 넣지 않는다.
